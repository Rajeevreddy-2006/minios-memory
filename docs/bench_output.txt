=============== 1. KERNEL HEAP: kmalloc (buddy + slab) vs glibc malloc ===============
  3000000 alloc/free operations, ~20000 live objects, sizes 24..1000 B

                                ns / op    per-object overhead   footprint / live bytes
  MiniOS kmalloc (slab)            25.8                  1.22x                    1.26x
  glibc malloc                     25.4                  1.05x                    1.11x
  (failed MiniOS allocations: 0)
  per-object overhead = bytes the live objects occupy after header / size-class rounding;
  footprint = total memory the allocator holds, which also counts partly-filled slab pages / free chunks.
  Caveat: both run in user space on the same op sequence. glibc is a different design
  (arenas, tcache) tuned for threads; this shows trade-offs, not a claim to beat it.
  MiniOS's kmalloc rounds up to power-of-two classes, which is where its extra overhead comes from
  (the compressed pool uses finer-grained classes for exactly this reason).

  Buddy allocator fragmentation: random order-0..3 alloc/free held near 70% utilization
    2887 of 4096 frames in use; 1209 free, split across 41 blocks; largest free block: order 9 (2048 KiB)
    external fragmentation index 0.58 (0 = one big block, 1 = all free memory in single frames)
    after freeing everything: 4096 free in 4 maximum-size blocks (fully coalesced: yes)

=============== 3. EFFECTIVE RAM: SAME BUDGET, WITH AND WITHOUT A COMPRESSED POOL ===============
RAM budget: 256 frames (1024 KiB). Data: 400 pages (1.56x the budget): 20% zero, 5% same-byte, 15% sparse,
15% records, 15% prose, 10% pointer arrays, 20% random. 150000 accesses, 85% to a 96-page hot set, 25% writes.
Pool frames are carved OUT of the budget, so every pool frame is one fewer resident page.

  Best pool size on SSD: 32 frames -> 0.90 s vs 1.57 s without compression (1.7x faster)
